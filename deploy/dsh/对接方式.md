# dsh 侧对接方式（空白 harness → 可被本项目调用）

目标：在一台**空白的 DeepSeek Harness（dsh）**上，把 OneBot v11 反向 WS 通道打通，
让本项目的 `dsh` 工具能把任务发过去、并把结果取回。

本文档只用占位符，不含任何具体项目的路径、token、QQ 号；照着替换即可。

```
本项目 tool-runtime ──(OneBot v11 反向 WS 客户端)──▶ dsh-onebot-qq ──▶ dsh agent ──▶ 模型
         ▲                                                │
         └──────────── send_msg（回复） ◀─────────────────┘
```

---

## 0. 需要准备的信息

| 占位符 | 含义 | 建议取值 |
|---|---|---|
| `<BOT_SELF_ID>` | 机器人自身 QQ 号（dsh 侧 `botQQ`），用来看 `@` 与 meta 事件 | 任意数字，如 `10001` |
| `<SENDER_ID>` | 本项目发信人 id（必须进 `adminUsers`，因为 `/workspace` 仅管理员可用） | 任意数字，如 `10086` |
| `<ACCESS_TOKEN>` | 通道鉴权 token，两侧必须一致 | 随机串，见下 |
| `<DSH_WORKSPACE_ROOT>` | 工作区在 Windows 侧看到的路径（`Z:\...` 或 `\\host\share\...`） | 本机真实目录 |
| `<PORT>` | 反向 WS 端口 | `8644`（别与 NapCat 常用的 8643 冲突） |

生成 token（任选）：

```powershell
# PowerShell
-join ((1..32) | ForEach-Object { '{0:x}' -f (Get-Random -Max 16) })
```

---

## 1. 装插件

```powershell
cd "$env:USERPROFILE\.dsh\profiles\web"
pnpm add dsh-onebot-qq          # 官方源超时：pnpm add dsh-onebot-qq --registry=https://registry.npmmirror.com
```

然后把插件登记进 profile 的 `package.json`（`dsh.profile.bundles` 数组里加一项）：

```json
"dsh": { "profile": { "bundles": [ "...", "dsh-onebot-qq" ] } }
```

> 插件自带 `dsh.bundle.patch`，会自己 insert 主入口与设置页 remote；
> **不要再手动 insert 同一插件**，重复注册会崩溃循环。

---

## 2. 配通道

把 `onebot.patch.yml` 里那一段整块粘进 `$env:USERPROFILE\.dsh\profiles\web\cordis.patch.yml`
（同 id 的 config 覆盖是**整块替换**，所以要么不写、要么写全）。

关键项说明：

| 键 | 作用 |
|---|---|
| `mode: reverse` + `host/port` | 本插件监听，等客户端拨进来 |
| `accessToken` | 必须与 `<ACCESS_TOKEN>` 完全一致 |
| `botQQ` | `= <BOT_SELF_ID>` |
| `adminUsers` | 含 `<SENDER_ID>`，否则 `/workspace`、`/permission` 会被拒 |
| `groupPolicy: open` / `requireMention` | 本项目用**群 chat** 承载会话隔离，`requireMention: true` 时需要 `@`（客户端会带 `at` 段） |
| `workspacePath` | 会话默认工作目录（每个 chat 可用 `/workspace` 覆盖） |

---

## 3. 重启并确认

```powershell
# 停掉正在运行的 dsh web，然后重新起
dsh web --port <WEB_PORT>
```

启动日志里应出现：

```
[dsh-onebot] mounted (mode=reverse, ...)
[dsh-onebot] reverse WS server listening on ws://127.0.0.1:<PORT> (path /ws or /)
[dsh-onebot] bridge ready (N resumed chat(s))
```

检查端口：

```powershell
Get-NetTCPConnection -LocalPort <PORT> -State Listen
```

> ⚠️ dsh 每次启动都会换 Web 访问 token；旧页面必须用新打印的 `?token=...` URL 刷新，
> 否则页面上所有发送都会失败。

## 4.（可选）把某个 chat 绑到一条已有会话

插件把 chat→session 的映射存在
`%USERPROFILE%\.dsh\media\onebot\chat-sessions.json`，并且**只在启动时**读一次。

用 `dsh-bind.ps1` 改绑定：

```powershell
# 看有哪些会话（按活跃度排序）
.\dsh-bind.ps1 -List

# 按标题关键字 + 目录收窄，先 dry-run 看会写什么
.\dsh-bind.ps1 -Title "<标题关键字>" -Cwd "<目录名>"

# 停 dsh → 写绑定（无 BOM、原子替换）→ 再起
.\dsh-bind.ps1 -Id <session-id 前缀> -Apply -Restart

# 只想重启
.\dsh-bind.ps1 -RestartOnly
```

**纪律（踩过的坑，务必遵守）**

1. 必须 **停 dsh → 写文件 → 起 dsh**。跑着改一定会被插件用内存状态回写；
2. 写文件**不能带 BOM**：PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会加 BOM，
   插件 `JSON.parse` 会抛错、被静默吞掉 → 日志出现 `bridge ready (0 resumed chat(s))`
   并反过来把文件写成 `{}`；
3. 不要绑「正在被 Web 使用」的会话：一条会话同时只有一个活回合，另一个 agent
   resume 过来会报 `transport failed`。

## 5. 验证

先做一个假插件自检（不依赖 dsh，只验协议）：

```bash
python tools/dsh_client_test.py        # 本项目 tool-runtime 容器内
```

再从本项目发一条真实任务：

```
工具调用:dsh|.|回一句 ok
```

期望：dsh 侧 console 出现
`[dsh-onebot] followup from group:<CHAT_ID>: ... <user_message qq="<SENDER_ID>">`，
随后本项目拿到回复。

## 6. 排障表

| 现象 | 原因 | 处理 |
|---|---|---|
| `bridge ready (0 resumed chat(s))` | 映射文件空/带 BOM，或目标 session 被 retire | 停 dsh → 重写映射（无 BOM）→ 起；必要时清 `retired-sessions.json` |
| `模型回合出错: DeepSeek Messages transport failed` | 目标会话有另一个 agent 在跑（Web 端占用） | 换一条没在用的会话，或改用独立会话 |
| 本项目返回「会话忙」 | 目标会话有活回合 | 等它空闲，或带工作区走独立会话 |
| `GetNamedSecurityInfoW failed (Win32 1)`（pwsh 起不来） | 会话 cwd 在 UNC/网络路径，沙箱读不到 ACL | 把 cwd 换成本地盘，或在会话里给 `danger-full-access` |
| 页面所有发送失败 | dsh 重启后 Web token 变了 | 用新 `?token=...` 刷新 |
| 客户端连上又被踢 | 同一端口有第二个反向 WS 客户端（如 NapCat） | 一个端口只留一个客户端 |

---

## 7. 已知限制

1. **一条会话同时只能有一个活回合**：与其并行使用必然会撞车；
2. **会话隔离靠群 chat**：`chatId = group:<数字>`，本项目按工作区路径派生，一个工作区一条会话；
3. **`/workspace`、`/permission` 仅管理员可用**：`<SENDER_ID>` 必须在 `adminUsers` 里；
4. **每次重启换 Web token**、**映射只在启动时加载** —— 这两条决定了所有运维动作的顺序。
