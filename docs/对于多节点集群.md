# 对于多节点集群

My_Agent_MSA 默认面向 Docker Desktop + WSL2 的单节点场景。若要在多节点 Kubernetes 集群部署，需要了解以下约束：**节点亲和**、**宿主机/WSL 网络依赖**、**副本数限制**。

## 一、节点亲和（必须固定节点）

### `openviking-server` — 唯一硬性同机服务

```yaml
# deploy/services/openviking-server.yaml
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - key: kubernetes.io/hostname
      operator: In
      values: ["desktop-worker"]   # 已写死节点

volumes:
  - name: store-local
    hostPath:                      # 节点本地磁盘，非共享
      path: /var/lib/openviking/store
```

- **原因**：vectordb store 是 **hostPath 卷**（节点本地磁盘），不是 NFS。换节点 = 索引数据丢失。
- **结论**：openviking-server 与它的数据必须**永远在同一节点**。
- **改造方案**：把 `store-local` 改为 NFS 子目录 + 删除 nodeAffinity，换取可迁移性（需确认 OpenViking 对共享存储的并发行为）。

## 二、宿主机 / WSL 网络依赖（非「同机」，但需同网络可达）

| 服务 | 依赖 | 单节点（Docker Desktop） | 多节点 |
|---|---|---|---|
| model-proxy-service | 宿主机 Ollama `host.docker.internal:11434` | 自动可用 | 需调度到能访问宿主机 IP 的节点，或改用节点 IP / NodePort |
| qq-llbot-service | 宿主机 LLBot `host.docker.internal:5600` | 自动可用 | 同上 |
| OpenViking embedding（ov.conf） | 宿主机 Ollama `:11434` | 自动可用 | 同上 |
| tool-runtime-service | WSL sshd（SSH 执行 clawhub/codex） | 自动探测 WSL IP | 任意节点，只要该节点能路由到 WSL IP |
| 全部 Pod | NFS（WSL 2049） | 自动 | 所有节点需能访问 NFS server（WSL IP:2049） |

> `host.docker.internal` 是 Docker Desktop **单节点**特性；多节点集群中需把它替换为宿主机节点 IP 或经 NodePort 暴露，并给相关服务加 `nodeSelector`。

## 三、副本数限制

### 🔒 必须为 1（多副本会直接出错）

| 服务 | 原因 |
|------|------|
| **task-scheduler-service** | 调度核心是**内存态**：`USER_QUEUES`、`BUSY_USERS`、槽位计数、事件总线都在进程内。多副本 = 用户队列分裂、同一事件被多个订阅者重复推送、槽位调度错乱 |
| **timer-task-service** | 后台扫描线程读**共享 NFS** 任务目录且无分布式锁，多副本会**重复执行**同一批到期定时任务 |
| **qq-llbot-service** | 固定 `SUBSCRIBER_ID` 订阅 scheduler 事件流，多副本对同一频道各收一份 → **QQ 消息重复推送** |
| **openviking-server** | hostPath 本地存储，多副本索引各自分裂 |

### ⚠️ 建议为 1（多副本需改造，否则有状态错乱）

| 服务 | 原因 |
|------|------|
| **agent-orchestrator-service** | AgentRuntime 有进程内状态（`default_agent` 映射、会话缓存）；同一会话请求打到不同副本会上下文错乱（虽有共享 NFS，但运行时状态在内存） |
| **gateway-backend-service** | SSE 会话无粘性：用户连到副本 A，scheduler 事件推给副本 B 时 A 收不到 → 丢消息（需共享事件总线 + 粘性会话才可多副本） |
| **tool-runtime-service** | 共享 workspace / PROCESS 目录并发写 + 端口代理（5800-5899）状态在单副本内 |
| **user-service** | 用户 JSON 存 NFS 但无文件锁，多副本并发写同一用户文件有覆盖风险 |

### ✅ 可多副本（无状态）

| 服务 | 说明 |
|------|------|
| frontend-service | 静态 nginx，可任意扩展 |
| image-assets-service | 静态 nginx |
| model-proxy-service | 无状态，每次请求读配置 |
| openviking-context-service | 无状态（读 openviking-server + user-service） |
| istio-ingressgateway | 入口网关，可多副本 |

> dashboard-service 虽无状态可 >1，但作为管理面板单副本足够。

## 四、多节点部署建议

1. **openviking-server**：固定一个专用节点（接受 hostPath），或改造为共享存储 + 去 nodeAffinity
2. **宿主机依赖**：model-proxy / qq-llbot 用 `nodeSelector` 固定到能访问宿主机 IP 的节点；把 `host.docker.internal` 替换为宿主机节点 IP
3. **NFS 单点**：NFS server 在 WSL，天然单点。多节点建议挪到独立存储（NAS / 云盘），并确保所有节点可达 2049
4. **单例服务**：task-scheduler / timer-task / qq-llbot / openviking-server 保持 `replicas: 1`，并可用 Pod 反亲和避免与其它副本同节点（防止整组故障）
5. **HA 前提**：当前所有服务 `replicas: 1`，多节点只是「分布」而非「高可用」。若要 HA，需先解决 task-scheduler 的内存态（外部队列/分布式锁）、gateway 的事件分发（粘性/共享总线）、agent-orchestrator 的会话路由
